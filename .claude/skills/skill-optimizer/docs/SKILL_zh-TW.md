# 技能優化器 Skill Optimizer

讓技能的攜帶成本更低、也更容易遵循，同時不遺失任何 Claude 無法自行推想出來的內容。精簡不等於拆分：目標是每個正確結果所耗費的 token 更少，而不是讓 SKILL.md 的行數最少。

## 為什麼是這些規則

- **描述是整個技能庫的共同成本。** 每一則描述都會出現在每個 session（工作階段）的技能清單裡，而這份清單有一個共用的預算（在 Claude Code 中約為上下文視窗的 1%）。一旦超出，最少被使用的技能就會失去描述，不再能穩定觸發。
- **規則要放在一定會被讀到的地方。** 技能觸發時會載入整份 SKILL.md，但參考檔只有在 Claude 決定打開它時才會被讀取；而且在上下文壓縮（context compaction）之後，只有技能的前 ~5,000 個 token 會被重新附上。在一項 2026 年的研究中，把技能拆成一份簡短的主檔加上多個檔案，對探索型任務略有幫助，對限制條件繁多的任務則有害：分散在多個檔案裡的規則會被漏掉。
- **搬走贅述，不等於刪掉它。** 移到 `references/` 的文字照樣會被讀取、照樣要付出成本。應該改為刪掉 Claude 本來就知道的內容；在 2026 年的基準測試中，巨細靡遺的文件相較於精簡的技能，幾乎沒有帶來任何提升。
- **結構不足為證。** 技能看起來多整齊，幾乎預測不了它有沒有幫助，所以要檢查行為，而不只是看版面。

## 工作流程

### 階段 0：快照

動手之前先把技能複製一份（`cp -r <skill> <workspace>/skill-snapshot/`，工作區放在 repo 根目錄的 `.skill-workspaces/` 底下），並記下描述的長度與 SKILL.md 的行數。

### 階段 A：描述

依照技能庫的規則改寫描述，再列出改寫前後的對照並附上字元數：

1. 以約 300 字元為目標，只有在技能有容易混淆的相鄰技能時才放寬到 500；絕不超過 1,024 字元（Agent Skills 規格；Claude.ai 與 API 會拒絕更長的描述）。
2. 順序：用一句以動詞開頭的話說明它做什麼 → 「Use when …」加上使用者實際會輸入的詞句（中文與英文）→ 針對最容易混淆的相鄰技能，最多一到兩條「not for X (→ other-skill)」轉介。
3. 刪除人設頭銜（「Elite…」「Chief…」）、流程指令（「MUST ALWAYS…」「generates immediately」）、對路由沒有幫助的功能清單，以及重複的同義詞。
4. 保留真實請求會用到的每一個觸發詞。如果判斷不出哪些重要，就問使用者，或者使用該技能的 trigger eval（觸發評測），如果它有的話。
5. 不可出現 `<` 或 `>`（驗證器會拒絕它們，而且 Claude Code 會把它們顯示成 `&lt;` / `&gt;`），也不可出現「冒號後接空格」，它會讓 Claude.ai 上傳這類嚴格的 YAML 解析器失敗。

### 階段 B：本文——把所有內容分進三個籃子

1. **留在 SKILL.md，並放在靠前的位置：** 一行的目的說明、硬性規則（禁止事項、規定格式、數值限制、輸出語言）、核心工作流程、輸出範本，以及 `## Gotchas`（常見陷阱）段落（缺少的話就補上一個）。
2. **移到 `references/`**（只放一層；檔案超過 100 行時加上目錄）：型錄、詞彙表、風格辭典、冗長的範例庫、只與特定變體有關的細節、只是偶爾才需要的背景知識。在 SKILL.md 中加上指引，說明*何時*該讀哪個檔案（「When the user picks style X, read `references/x.md`」）。
3. **刪除：** Claude 本來就知道的內容（泛泛的技法講解、通用的提示詞建議）、重複陳述、精神喊話式的贅文、人設樣板文字。

在變更摘要中列出每一項刪除，讓使用者可以否決；任何內容都不能悄悄消失。把全大寫的 MUST/NEVER 改寫成一條平實的規則加上它的理由，只在格式或安全限制真正需要的地方保留強調。沒有目標行數：在規則容許的範圍內，讓 SKILL.md 越短越好，而且絕不超過 500 行。

### 階段 C：可攜性與整潔

- Frontmatter 只含 `name`（與資料夾名稱完全相同）、`description`、`license`、`compatibility`、`metadata` 和 `allowed-tools`。只適用於 Claude Code 的可見度設定（`name-only`、`user-invocable-only`）應寫在設定鍵 `skillOverrides` 裡。
- 使用不綁定特定工具的措辭（寫「read `references/x.md`」，而不是「invoke view_file」），以及相對於技能資料夾的路徑，而不是 `.agent/skills/...` 或使用者的絕對路徑。
- 技能裡不放 README、changelog 或安裝說明，也不放 API 金鑰或 token。
- `references/` 裡的每個檔案都要有 SKILL.md 指向它，而 SKILL.md 指向的每個檔案也都必須存在。`docs/` 維持不被引用。
- 執行 `python3 <skill-creator>/scripts/quick_validate.py <skill>`，並修正它回報的問題。

### 階段 D：檢查行為

- **只改了描述：** 如果技能有 trigger eval，就重跑一次。如果沒有，就寫下三個應該觸發它的請求，以及兩個相近但不該觸發的請求（near-miss），逐一對照新的措辭檢查。接著依 skill-creator 內規第 2 條的方法，檢查整份清單的大小。
- **本文內容有搬移或刪除：** 如果技能有 `evals/`，就透過 skill-creator 的迴圈，分別在快照與新版本上執行並加以比較。如果沒有，就用兩個貼近實際的提示詞在兩個版本上各跑一次，比較輸出有沒有遺失規則，並提議把這些提示詞存成測試案例。

接著交給 **skill-translator**，讓 `docs/SKILL_zh-TW.md` 與新的 SKILL.md 一致。

## 輸出

一份以使用者的語言撰寫的變更摘要：
- description：字元數（前 → 後），以及新的文字
- SKILL.md：行數（前 → 後）
- 搬移：什麼內容移到了哪個參考檔
- 刪除：每一項被移除的內容
- 檢查：驗證器的結果，以及行為檢查的結果

## Gotchas（常見陷阱）

- 「優化這段提示詞」或「幫我優化圖片 prompt」講的是提示詞，不是技能：交給提示詞類的技能處理。
- 把「不要呼吸鏡」這類規則移進 `references/`，會讓每一次沒打開那個檔案的執行都看不到它。規則要留在 SKILL.md。
